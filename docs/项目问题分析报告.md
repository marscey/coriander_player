## 二、详细分析

### P0-1 移动端测试资产未纳入版本控制，且目录名拼写错误

**现象**

- 实际测试目录为 `test/meastro/`（`meastro` 为拼写错误，正确拼写应为 `maestro`），内含 19 个文件。
- `.gitignore` 第 62 行忽略了 `test/meastro/`，因此**只有 `config.yaml` 被 git 跟踪，其余 18 个流程 YAML 全部未纳入版本控制**：

```
$ git ls-files test/meastro
test/meastro/config.yaml

$ git status --ignored --porcelain test/meastro | wc -l
18
```

- 被忽略的流程文件包括 `flow.yaml`、`smoke_test.yaml`、`nav_test.yaml`、`comprehensive_ui_test.yaml`、`edit_tag_test.yaml`、`artist_detail_immersive_test.yaml` 等，即项目文档中宣称的主力回归用例。
- 同时 `CLAUDE.md` 有 6 处命令指向**不存在的路径** `test/maestro/`（第 37、38、138、154、157、160 行），按其指引执行 `maestro test test/maestro/` 会直接失败。

**影响**

- 移动端回归测试无法随代码分发、无法在 CI 复现、换机即丢失。
- `config.yaml` 已被跟踪，但它引用的流程文件不在仓库内，属于"半提交"状态，危害大于完全不提交。
- 文档给出的测试命令不可执行，新人按文档操作必然踩坑。

**修复建议**

1. 将目录 `test/meastro/` 重命名为 `test/maestro/`（`git mv`）。
2. 删除 `.gitignore` 第 62 行 `test/meastro/` 规则，将流程 YAML 纳入版本控制。
3. 同步修正 `CLAUDE.md` 中的路径引用（若目录已正名，则第 138 行起的说明自然成立）。
4. 若担心测试产物污染仓库，改为只忽略 `test/maestro/reports/`、`*.png` 等产物而非整个目录。

### P0-2 当前检出缺少 `.dart_tool/`，静态分析输出不可用

**现象**

仓库根目录不存在 `.dart_tool/`，也不存在 `.dart_tool/package_config.json`，即从未在本检出执行 `flutter pub get`。此时执行 `dart analyze lib` 的结果：

```
10937 issues found.
  error:   10495
  warning:   442
```

错误按规则分布：

| 规则 | 数量 | 性质 |
|---|---|---|
| `undefined_identifier` | 3777 | 伪错误 |
| `undefined_method` | 2964 | 伪错误 |
| `undefined_class` | 1087 | 伪错误 |
| `uri_does_not_exist` | 837 | 根因：包解析失败 |
| `creation_with_non_type` | 684 | 伪错误 |
| `override_on_non_overriding_member` | 419 | 伪错误 |

根因是最基础的包解析失败，例如：

```
error - app_preference.dart:4:8 - Target of URI doesn't exist:
        'package:coriander_player/app_settings.dart' - uri_does_not_exist
```

连本项目自身的 `package:coriander_player/...` 都无法解析，后续的 `undefined_*`、`override_on_non_overriding_member` 全是连锁产物。

**连带误判示例**：分析器报告 `lib/play_service/lyric_service.dart:50` 与 `:52` 为 `dead_code`，但这两行实际位于 `if (PlatformHelper.isIOS || PlatformHelper.isMacOS)` 内、依赖 `SyncLyricLine` / `UnsyncLyricLine` 类型判断。因相关类型未解析成功，分析器才误判为不可达——**该告警为假阳性，不应据此改代码**。

同理，`warning - src/bass/bass_player.dart:38 - '_bassPlugins' isn't referenced` 等 `unused_*` 告警也需在包解析正常后复验，当前不可采信。

**影响**

- 无法获得真实的静态分析基线，代码质量门禁形同虚设。
- 若有人误采信这 10937 条输出，会围绕假阳性做无意义的"修复"。
- `CLAUDE.md` 的「Lint: `dart analyze`」一节未说明必须先执行 `flutter pub get`，容易复现此问题。

**修复建议**

1. 执行 `flutter pub get` 生成 `.dart_tool/package_config.json`。
2. 用 `flutter analyze`（而非 `dart analyze`）作为标准 lint 命令，二者对 Flutter 项目的解析行为不同。
3. 在 `CLAUDE.md` 的 Lint 小节补充前置条件说明。
4. 建议将 `.dart_tool/` 的缺失纳入环境自检清单（`flutter doctor` 不会覆盖此项）。

### P1-1 播放引擎支持性判断存在两个真相源

**现象**

"哪些平台支持 BASS 引擎"这一判断被实现了两次，且都是硬编码的私有逻辑：

- `lib/play_service/engine/player_engine_factory.dart:20-22`

```dart
static bool _isBassSupported() {
  return Platform.isWindows || Platform.isMacOS || Platform.isLinux;
}
```

- `lib/platform_dependency_manager.dart:47-59`（`getSupportedPlayerEngines()`）与 `:67-74`（`getRecommendedPlayerEngine()`）重复了同一组平台判断。

两者的消费方也不同：

| 消费方 | 位置 | 读取来源 |
|---|---|---|
| 引擎实例创建与回退 | `player_engine_factory.dart:31` | `_isBassSupported()` |
| 设置页引擎选项渲染 | `lib/page/settings_page/player_engine_selector.dart:26` | `PlatformDependencyManager` |
| 启动时校正已配置引擎 | `lib/main.dart:244-251` | `PlatformDependencyManager` |

注：`CLAUDE.md` 架构章节还记载了 `PlayerEngineFactory` 会依据 `PlatformDependencyManager` 选择引擎，但实际代码中二者**无任何依赖关系**，文档描述与实现不符。

**影响**

- 两份判断一旦漂移（例如未来为 Linux 关闭 BASS 支持），会出现"设置页仍展示 BASS 选项，但选中后被静默回退到 MediaKit"的错位状态。
- 三个消费路径分别读取不同来源，排查此类问题时需同时检查两处。

**修复建议**

统一为单一来源：让 `PlayerEngineFactory` 依赖 `PlatformDependencyManager.getSupportedPlayerEngines()`，删除 `_isBassSupported()`；或反向将平台判定下沉到独立的 capability 常量，两处共同引用。同时修正 `CLAUDE.md` 中对该协作关系的描述。

### P1-2 `PlatformDependencyManager` 为空壳实现

**现象**

该类被 `main.dart:242` 在启动流程中正式调用，但从实现看是未完成的占位代码：

1. **设备信息永远为 null**。`lib/platform_dependency_manager.dart:224-234`：

```dart
Future<dynamic> _importDeviceInfoPlus() async {
  try {
    // 在Dart中，我们不能真正地动态导入库
    return null;   // <-- 恒返回 null
  } catch (e) { ... return null; }
}
```

该方法是 `DeviceInfoPlusPlugin` 下 `androidInfo` / `iosInfo` / `windowsInfo` / `macosInfo` / `linuxInfo` 五个 getter 的唯一数据来源，全部因此恒返回 `null`。`initialize()` 中赋值的 `_deviceInfo` 随之恒为 `null`。

2. **平台初始化钩子无实效**。`_initializeAndroidDependencies` / `_initializeIOSDependencies` / `_initializeMacOSDependencies` / `_initializeLinuxDependencies`（第 77-113 行）仅输出一行日志，注释也自述"这里可以添加……初始化代码"。

3. **依赖声明与实际使用不符**。`device_info_plus` 在 `pubspec.yaml:66` 声明，仅被 `platform_dependency_manager.dart:4` import，而真正的 `DeviceInfoPlugin` 类在全项目中**零引用**（该 import 实际未被使用）。这意味着一个平台插件依赖被白列入构建。

4. **对外输出恒定错误**。`getPlatformInfo()`（第 130-137 行）依赖 `_packageInfo` 与设备信息，其中设备部分必然输出"未知"。

5. `checkRuntimePermissions()`（第 116-127 行）三个分支全部 `return true`，未做任何实际检查。

**影响**

- 启动流程中多了一次无收益的异步初始化及包信息查询。
- 任何依赖设备信息做差异化行为的后续开发都会踩空（拿到 `null` 而非报错，属于静默失败）。
- 多余的平台插件依赖会进入 iOS/Android 构建产物与隐私清单，对上线合规有潜在影响。

**修复建议**

二选一：

- **补齐**：将 `_importDeviceInfoPlus()` 改为直接调用 `DeviceInfoPlugin()` 的真实实现（该插件本就支持全平台，无需"动态导入"）；补全或删除空的平台钩子。
- **裁剪**：若设备信息确无需求，删除 `DeviceInfo` / `DeviceInfoPlusPlugin` / `checkRuntimePermissions` 及 `device_info_plus` 依赖，仅保留引擎支持性判断能力（与 P1-1 合并处理）。

### P2-1 死代码与并行重复实现

**死代码**

`lib/page/album_detail_page.dart:13` 的 `AlbumDetailPage` 已无任何调用方。全项目搜索结果显示，除自身定义外，唯一提及是 `lib/page/uni_detail_page.dart:12` 的一行文档注释：

```
lib/page/uni_detail_page.dart:12:/// `ArtistDetailPage`, `AlbumDetailPage` 页面的主要组件。
lib/page/album_detail_page.dart:13:class AlbumDetailPage extends StatelessWidget {
```

实际路由使用的是 `lib/page/album_detail_page_new.dart:13` 的 `AlbumDetailPageNew`（见 `lib/entry.dart:220` 与 `:378`）。

**并行重复实现**

艺术家详情页存在两套完整实现，按主题模式分流：

| 实现 | 文件 | 路由位置 | 使用场景 |
|---|---|---|---|
| `ArtistDetailPage` | `lib/page/artist_detail_page.dart:13` | `lib/entry.dart:207` | Material 3 分支 |
| `ArtistDetailPageV3` | `lib/page/artist_detail_page_v3.dart:61` | `lib/entry.dart:357` | Liquid Glass 分支 |

`ArtistDetailPageV3` 单文件 1438 行，内含 5 个私有组件类。专辑详情页则相反——两个分支都指向 `AlbumDetailPageNew`，没有 Glass 专用实现，这也解释了两处路由为何引用同一类。

**影响**

- `AlbumDetailPage` 属纯粹的历史残留，会误导后续排查"专辑详情页在哪"。
- 艺术家详情页的双实现是有意的主题分流，但意味着该页面的任何逻辑修复必须改两遍，目前无任何注释或文档标注这一约束。

**修复建议**

1. 删除 `lib/page/album_detail_page.dart`，并同步清理 `lib/uni_detail_page.dart:12` 注释中的错误引用。
2. 对双实现方案：在 `entry.dart` 的两处路由旁添加注释说明分流关系，并将两实现的公共逻辑（数据装配、播放全部、排序）下沉为共享 helper，避免行为漂移。

### P2-3 `CLAUDE.md` / `AGENTS.md` 未被版本控制

`.gitignore` 第 54 行忽略 `CLAUDE.md`，`AGENTS.md` 同样未被跟踪（`git ls-files` 结果均为 0）。这两个文件承载了构建命令、架构说明、测试流程、编码约定，是当前事实上的团队规范来源。

**修复建议**

移除 `.gitignore` 第 54 行，将 `CLAUDE.md` 纳入版本控制；`AGENTS.md` 同理。如担心个人偏好混入，可拆分为"团队规范（跟踪）"与"个人偏好（忽略，如 `.claude/`）"两层。
